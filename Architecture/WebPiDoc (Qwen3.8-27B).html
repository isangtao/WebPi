01Overview & design goals

WebPi is a web-based autonomous coding agent. The user describes what they want to build in a chat box; an LLM (any OpenAI-compatible server, e.g. a local one at http://localhost:1234/v1) responds with text and function calls. Function calls are executed against a virtual file system that exists purely in browser memory (files object + folders Set), and the results are streamed back to the model until it stops calling tools — the classic reason → act → observe → repeat agent loop.

  • Air-gapped core: all application logic, CSS and the ZIP writer are embedded; the only network call is the LLM API request itself.
  • Four-pane IDE layout: Files (top-left), Chat (bottom-left), Editor (top-right), live Preview (bottom-right), split by a draggable cross-handle (CSS custom properties --split-x / --split-y); on mobile the panes collapse into tabs.
  • Safe-by-default tooling: every mutating operation first captures a deep-copy snapshot, and every tool call in the chat gets a one-click ↩ Rollback button.
  • Live sandbox preview: the generated app runs in a sandboxed <iframe> whose HTML has the project's own <link rel="stylesheet"> and <script src> assets inlined, so multi-file projects render without a server.
  • Persistence without a backend: settings persist to localStorage; whole sessions (files, chat, snapshots) can be exported/imported as JSON; the project can be exported as a real .zip built byte-by-byte by a hand-written PKZIP implementation.

02High-level architecture (component view)

The single HTML file contains three cooperating layers. The UI layer (header, panes, modals) only ever talks to the agent core through a handful of global functions. The agent core orchestrates the in-memory workspace, which is the single source of truth: the file tree, editor and preview are all just projections of the files / folders state.

03Data model (class view)

The code is plain procedural JavaScript (one class: MinimalZip), but the implicit data structures are clear. chatHistory is the backbone: it stores user, assistant, tool and system messages, each carrying the OpenAI tool-calling metadata (tool_calls / tool_call_id / name) plus UI state (which panels are expanded) and a back-reference to the snapshot taken just before the tool ran — which is what powers the per-call Rollback buttons.

The seven tools exposed to the model are: read_file, write_file, edit_file (exact, uniqueness-checked search-and-replace), delete_file, create_folder, delete_folder and move_file. Their JSON-Schema definitions live in AGENT_TOOLS and are sent with every request.

04Agent loop — stream, decide, act (sequence)

Pressing Send calls handleSendPrompt() → runAgentLoop(). The loop runs for at most 25 turns. Each turn: build a budgeted message payload, POST to /chat/completions with stream: true and the tool schemas, consume the SSE stream while incrementally updating the DOM, then — if the model emitted tool_calls — snapshot and execute each one, append the results as role: "tool" messages, and iterate. No tool calls means the task is done. A Stop button aborts the in-flight request through an AbortController.

Fallback mode. If the model ignores the tool-calling API but prints a ```tool_name … ``` fenced code block in its text, parseFallbackCalls() extracts and executes it anyway — so non-tool-aware local models still work.

05SSE stream parsing (activity)

The response body is consumed with response.body.getReader() + a TextDecoder. Because chunks can split anywhere, bytes are appended to an sseBuffer, split on \n, and the last (possibly incomplete) line is kept for the next chunk. Each data: line is JSON-parsed; deltas of reasoning_content/reasoning, content and tool_calls are merged. Tool calls arrive fragmentary — name and argument JSON are concatenated per stream index into a toolCallMap until the stream ends, when the complete calls are validated and normalized.

    E -- no --> D2["skip blank, comment or DONE lines"]
    D2 --> B

    F --> G["store finish_reason if present"]
    G --> H["delta.reasoning? append to thinking buffer"]
    H --> I["delta.content? append to raw buffer"]

    J --> K["separateThinking: lift think tags out of content"]
    K --> L["update streaming DOM + status bar"]
    L --> B
    B -- reader done --> M([stream finished])

06Tool execution pipeline (flowchart)

executeTool(name, args) is a pure dispatcher with defensive semantics: it never throws to the model — every failure becomes a descriptive error string the LLM can react to. Note two robustness tricks: resolveToolName() lower-cases and fuzzy-matches tool names (so "Write_File!" still resolves), and edit_file normalizes CRLF→LF on both sides before counting occurrences of old_str — it refuses to run unless the match is exactly one.

07Context-window budgeting (activity)

Local models have finite context, so before every turn buildContextMessages() rebuilds the payload from scratch: tokens are estimated as length / 3.4 (a cheap heuristic), a reserve (min(maxTokens, 35% of window)) is kept for the model's output, and if the history exceeds the budget the oldest intermediate turns are dropped first. The original user prompt is always anchored, and leading orphan tool messages are trimmed so the API never sees a result without its call. 

flowchart TD
    S([start of turn]) --> A["read contextWindow and maxTokens from settings"]
    A --> B["reservedOutput = min(maxTokens, 35% of contextWindow)"]
    B --> C["budget = max(4096, contextWindow - reservedOutput)"]
    C --> D["locate the first real user message"]
    D --> E["slice chatHistory from that point"]
    E --> F["drop system, ui-error and empty turns"]
    F --> G["anchor first user message, rest = subsequentTurns"]
    G --> H["estimate tokens: chars / 3.4 for content and tool_calls JSON"]
    H --> I{total above budget?}
    I -- yes --> J{more than 2 later turns left?}
    J -- yes --> K["drop the oldest intermediate turn"]
    K --> H
    J -- no --> L{first leftover is a tool message?}
    I -- no --> L
    L -- yes --> M["shift orphan tool message out"]
    M --> L
    L -- no --> O([return: system + first user + kept turns])

08Agent lifecycle (state diagram)

The loop is guarded by isAgentRunning, a single AbortController and the 25-iteration cap. Errors (HTTP failure, CORS, network) are surfaced as a system chat bubble with a hint to check the local endpoint; user-initiated stops are reported cleanly.

09Snapshots & rollback (sequence)

captureSnapshot() deep-copies files (via JSON round-trip), the folders Set and the active file path into a timestamped entry. It fires automatically before every agent tool call and before every manual user mutation (save, new file, move, delete). Each resulting tool message therefore stores its snapshotId, and both the tool-call card and the tool-result card expose a ↩ Rollback button; the ⏱ History modal lists all checkpoints for bulk restore.

10MinimalZip — hand-rolled PKZIP (flowchart)

To keep the file dependency-free, ZIP export is implemented from scratch. Entries are written with the store method (no compression): a 30-byte local file header (magic 0x04034b50) followed by filename and raw bytes; then the central directory (one 46-byte entry per file, magic 0x02014b50); and finally the 22-byte end-of-central-directory record (0x06054b50). A 256-entry CRC-32 table (polynomial 0xEDB88320) provides integrity checksums; timestamps are packed into DOS format. The final byte stream is wrapped in a Blob of type application/zip — fully compatible with any unzip tool. 

flowchart LR
    A["add(name, content) x N files"] --> B["generateBlob()"]
    B --> C["build CRC-32 lookup table (256 entries)"]
    C --> D["per file: Local File Header 30 bytes + name + raw bytes"]
    D --> E["per file: Central Directory Entry 46 bytes + name"]
    E --> F["End Of Central Directory record, 22 bytes"]
    F --> G["Blob: application/zip, store method, no compression"]

Request anatomy. Every turn POSTs { model, messages, tools, tool_choice: "auto", stream: true, max_tokens, max_completion_tokens, reasoning_effort? } to <baseUrl>/chat/completions with a Bearer key — the standard OpenAI chat-completions contract, which is what makes any compatible server (Ollama, llama.cpp, vLLM, LM Studio, …) a drop-in backend.
Security model. Generated code runs inside <iframe sandbox="allow-scripts allow-modals allow-forms allow-same-origin allow-popups">; all user-generated HTML injected into the chat/tree UI passes through escapeHtml(); the agent can only touch the in-memory workspace — nothing ever leaves the browser except the API request.
